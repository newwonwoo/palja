# 원본 APK 균시차 함수 대조

2026-10-20에 해시를 검증한 8자어때 18.2.8 ARM64 실행 파일의 함수·객체 풀을 정적으로 분석했다. 원본 바이너리·전체 덤프는 저장소 밖에 보관한다.

## 확인한 동작

- 함수: `core/domains/manse/rules/get_equation_of_time_minute.dart`의 `getEquationOfTimeMinute`, 주소 `0xa01c1c`.
- 입력은 월·일 두 정수다. 연도·출생 시각은 이 함수의 입력이 아니다.
- 객체 풀 `0x18328`의 월별 표를 `month - 1`, `day - 1`로 조회한다. 월별 길이는 `31,29,31,30,31,30,31,31,30,31,30,31`로 총 366개다.
- 출력은 분 단위 정수이며 범위는 -14~16이다. 유효하지 않은 월·일은 예외 경로로 간다.
- 위치 선택 컨트롤러와 간단한 위치 선택 화면에서 이 함수를 호출하는 경로를 확인했다. 음력→양력 변환 및 전체 시각 보정의 호출 순서는 추가 대조가 필요하다.

## 현재 Palja와의 차이

Palja의 독립 계산 모드 `src/calendar/precise.js`는 NOAA 분수년 조화식으로 연속값을 계산한다. 아래는 원본 표와 2026년 UTC 정오의 기존 함수값을 비교한 예다. 시각 입력과 무관한 원본 표의 사실을 보여 주기 위한 비교이며 원본 앱의 사주 결과 일치 검증이 아니다.

| 월·일 | 원본 표의 분 값 | 현재 독립 함수의 분 값 |
|---|---:|---:|
| 01-01 | -3 | -2.90416896 |
| 02-11 | -14 | -14.19974768 |
| 11-03 | 16 | 16.36526029 |

기존 근사식을 단순히 정수 반올림하면 원본과 모든 날짜에서 같다고 가정할 수 없다. 출생정보의 기준 날짜, 경도 보정, 역사적 표준시·서머타임과의 순서를 확인하기 전에는 기존 계산 정책을 자동 교체하지 않는다.

## 남은 작업

- 원본 표를 사용하는 전체 입력·보정 경로의 날짜 기준 확인.
- 원본 실행에서 월 경계·윤일·자시 경계 합성 입력 검증.
- 원본 기준과 독립 기준을 구분한 명시적 계산 정책 설계 및 기존 데이터 회귀 확인.

`engine.equation`은 원본 정적 일부 확인으로만 갱신한다. 원본 표는 현재 Palja 계산 경로에 연결하지 않았고 원본과의 전체 동작 일치로 체크하지 않는다.
